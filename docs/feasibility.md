# 国标麻将拍照算番 + 记账 App：可行性评估

日期：2026-10-25
结论先行：**可行，值得做。** 算番和记账这两块是确定性的，技术上没有风险；真正的难点只有一个，就是"拍照识别牌"的准确率。只要产品上允许用户一键修正识别错的牌，并补充照片看不出的信息（自摸还是点炮、和的是哪张、门风圈风等），就能做出好用的产品。

> 说明：下文提到的开源库和竞品是基于我已有的知识，没有逐个联网核实最新状态，正式开工前需要再确认一遍。

---

## 1. 整体流程拆解

1. **拍照** → 2. **识别牌**（视觉模型）→ 3. **用户确认/修正**（必须有）→ 4. **补充信息**（照片拍不出来的）→ 5. **算番**（规则引擎）→ 6. **记账**（多局累计）

其中 1、2 有不确定性；3、4 是 UX 设计；5、6 是纯逻辑，可以做到 100% 正确。

## 2. 牌面识别：难度和对策

麻将牌只有 34 种（加上 8 张花牌共 42 类），类别少、图案固定，本质上是一个**小类别目标检测问题**，比通用识别容易得多。用 YOLO 一类的检测模型，在数据充足时单张牌的识别准确率做到 98% 以上是现实的。

但真实牌桌有这些麻烦：

| 难点 | 影响 | 对策 |
|---|---|---|
| 光线（暖光、反光、阴影） | 牌面反光时字看不清 | 数据增强；拍照时提示避开反光 |
| 角度（斜拍、透视变形） | 远端牌变小变形 | 引导用户"俯拍和牌者面前的牌"，不必拍全桌 |
| 遮挡、牌挨得紧 | 漏检、重复检测 | 检测后按行排序，并用"总牌数应为 14 张+杠"做校验 |
| 牌的样式差异（不同厂家、颜色、字体、大小） | 跨牌具泛化差 | 采集多种牌具的数据；允许用户少量标注自家牌后微调（后期） |
| 副露（吃碰杠）摆在旁边、横放的牌 | 需要判断哪几张是一组 | 识别出后让用户确认分组；横放牌本身也是"哪家打的"的线索 |
| 暗杠（两边扣着） | 背面看不出是什么 | 用户手动补 |
| 花牌 | 好识别，但常放得比较远 | 单独一行"花牌"，可手动加 |
| 牌已被推倒/打乱 | 无法区分手牌与牌河 | 只拍和牌者的牌，不拍全桌 |

**关键判断**：不要追求"拍一张全桌照片全自动"。产品设计成"**拍和牌者那一家的牌**"，识别结果以牌的图标排成一行展示，错了点一下改掉。这样即使模型只有 95% 的单牌准确率，用户也只需偶尔改一两张，体验依然比手动输入 14 张快得多。

**数据从哪来**：
- 网上已有一些麻将牌检测的公开数据集（Roboflow Universe、Kaggle 上有日麻/中麻牌的标注集），可以作为起点，但规模和多样性一般不够。
- 需要自己拍、自己标注：大约几千张照片、覆盖 5 到 10 套不同牌具，就能得到可用模型。可以用合成数据（把牌面图贴到不同背景、加透视和光照）来扩充。
- 上线后，用户的"修正"本身就是高质量的标注数据，可以持续改进模型（需征得用户同意）。

**另一条路：直接用多模态大模型（如 Claude / GPT 的视觉能力）识别**。优点是零训练，原型一天就能跑起来；缺点是对 14 张小而密集的牌，大模型目前容易数错、认错（尤其是条子和饼子的点数），而且每次调用有成本和延迟。**建议原型阶段用它快速验证，正式产品用专门训练的检测模型。**

## 3. 算番：确定性的，有现成开源库

国标麻将 81 番种、8 番起和，规则复杂但完全确定，适合写成规则引擎，不需要 AI。难点在于：
- 同一手牌有多种拆法（组合方式），要枚举所有拆法取番数最高的；
- "不计原则"（比如算了清一色就不再计无字等）和"套算一次原则"容易写错。

**现成的开源实现**：
- **ChineseOfficialMahjongHelper**（GitHub 上 summerinsects 的项目，C++）：国标麻将算番器，社区里用得很广，规则实现比较完整。
- **PyMahjongGB / MahjongGB**：北大 Botzone 平台的国标麻将 AI 比赛使用的算番库，基于上面的 C++ 实现做了 Python 封装。

做法：把 C++ 算番核心直接编进 iOS App（C++ 可以在 iOS 上原生调用），**离线运行，毫秒级出结果**。需要注意开源协议是否允许商用，如不允许就参考其逻辑自己实现，并用它做对照测试。

## 4. 照片拍不出来的信息，以及怎么补

| 信息 | 为什么需要 | UX 方案 |
|---|---|---|
| 自摸还是点炮，点炮的是谁 | 决定"不求人""自摸"等番，以及谁付钱 | 识别后两个大按钮："自摸" / "点炮"，点炮再选是哪家 |
| 和的是哪一张 | 影响"边张、坎张、单钓将"等 | 让用户点一下那张牌（默认最右边那张） |
| 门风、圈风 | 影响"门风刻、圈风刻" | 开局设定座位，App 按局数自动推算，无需每局输入 |
| 暗杠是什么牌 | 背面朝上 | 识别到背面牌时提示用户补选 |
| 吃碰杠的分组 / 是否门清 | 影响"门前清"等 | 识别出副露区后让用户确认 |
| 特殊情况：海底捞月、妙手回春、杠上开花、抢杠和、和绝张 | 照片无法判断 | 一排可选开关，默认全关 |

整个补充过程设计成"大多数情况点 1 到 2 下就完成"。

## 5. 记账设计

- **一场牌局** = 4 名玩家 + 座位 + 规则设置（底分、每番多少钱、是否有封顶等）。
- **每一局记录**：和牌者、点炮者/自摸、番数、番种明细、照片（可选），以及每人的输赢变化。
- **国标标准算分**（常见规则）：点炮者付"番数+8"，其他两家各付 8；自摸则另外三家各付"番数+8"。不同地方有自己的规矩，所以计分公式要**可配置**。
- **必备功能**：撤销/修改某一局、流局、查看每人累计输赢、牌局结束一键生成"谁该给谁多少钱"的结算单（自动做最少转账次数的简化）、分享截图到微信。
- **多人同步**（后期）：其他玩家扫码加入同一牌局，各自手机上看到实时账本。MVP 先只在一台手机上记，足够用。

## 6. 端侧 vs 云端

| | 端侧（手机本地） | 云端 |
|---|---|---|
| 识别模型 | Core ML 跑 YOLO 级别的模型，iPhone 上几十毫秒，可离线 | 换模型方便，但要联网、有服务器成本 |
| 算番 | **推荐端侧**，C++ 库直接编入 | 没必要 |
| 记账 | **推荐端侧**本地存储 + iCloud 同步 | 多人实时同步时才需要 |

**建议：正式版全部端侧**（牌桌上网络不一定好，而且无服务器成本、隐私好）。原型阶段可以先用云端大模型验证识别体验。

## 7. 竞品情况

- 已有不少**手动输入**的国标算番器（App Store 和微信小程序里搜"国标麻将算番"能找到多个），以及纯记账类 App/小程序（"麻将记账""打牌记分"类）。
- 日本麻将（立直麻将）领域已经有**拍照算点数**的 App，说明这个技术路线是走得通的。
- 国标麻将"拍照识别 + 算番 + 多局记账"三合一的成熟产品，我印象中还没有明显的头部选手，这是机会点（需要上线前再到 App Store 实际搜一遍确认）。

## 8. MVP 范围和大致工作量

**MVP（第一版）只做：**
1. 拍和牌者的牌 → 识别 → 可修正的牌面编辑器（识别不了也能纯手动选牌，保证兜底可用）
2. 补充信息面板（自摸/点炮、和张、特殊情况开关）
3. 算番并列出番种明细
4. 单机记账：设置 4 名玩家和计分规则、逐局记录、累计输赢、撤销、结算分享

**不做（以后再说）：** 全桌识别、多人实时同步、自家牌具微调、Android。

**粗略工作量（1 名熟练的 iOS 开发者，含 AI 辅助编程）：**

| 模块 | 时间 |
|---|---|
| 用多模态大模型做识别原型，验证体验 | 1 周 |
| 采集标注数据 + 训练检测模型 + 转 Core ML | 3 到 5 周（最大的不确定项） |
| 集成算番库 + 对照测试 | 1 到 2 周 |
| 牌面编辑器、补充信息 UI | 2 周 |
| 记账模块 | 2 周 |
| 打磨、测试、上架 | 2 周 |
| **合计** | **约 2.5 到 3.5 个月** |

如果先跳过自训练模型、直接用云端大模型识别 + 手动修正，**4 到 6 周可以做出能在牌桌上真实使用的版本**。

## 9. 主要风险

1. **识别准确率**：最大风险。用"可修正"的设计兜底，风险可控。
2. **规则地方差异**：各地打国标会有自己的小规矩（计分方式、是否算花），要做成可配置。
3. **开源算番库的协议**：商用前确认。
4. **赌博相关审核**：App Store 对涉及"赌钱"的描述比较敏感。产品文案上应表述为"计分/积分"，不要出现"赌""押注"等字样，也不做任何真实支付功能。

## 10. 建议的下一步

1. 我先用多模态大模型做一个识别小实验：你拍 10 到 20 张自己家牌桌上的和牌照片发给我，我测一下现成模型的识别准确率，这能最快判断识别这一步有多难。
2. 同时确认你们平时的计分规则（底分、每番多少、自摸怎么算、算不算花），我据此设计记账模型。
3. 结果满意再决定是否开始写代码、建仓库。
